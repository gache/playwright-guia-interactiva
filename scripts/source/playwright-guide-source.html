Glosario

Términos que vas a encontrar una y otra vez en esta guía y en la documentación oficial. Vuelve aquí cuando te topes con una palabra que no recuerdes.

Locator
Una receta para encontrar un elemento en la página cuando se necesite — no busca de inmediato, sino cada vez que lo usas. Ver sección 05.
Fixture
Un objeto que Playwright te entrega listo para usar en cada test, como page o request, sin que tengas que crearlo tú. Ver sección 26 para crear los tuyos.
Assertion (expect)
Una verificación que hace fallar el test si no se cumple — en Playwright, reintenta sola durante unos segundos antes de darse por vencida. Ver sección 07.
Auto-waiting
El comportamiento por defecto de Playwright de esperar a que un elemento esté visible, habilitado y estable antes de actuar sobre él.
Headless
Ejecutar el navegador sin interfaz visual (sin ventana) — más rápido, ideal para CI. Lo opuesto es "headed".
BrowserContext
Un perfil de navegación aislado, como una ventana de incógnito, con sus propias cookies y sesión. Ver sección 03.
Flaky test
Un test que a veces pasa y a veces falla sin que el código haya cambiado — casi siempre por esperas mal hechas (timeouts fijos, race conditions).
Race condition
Cuando dos eventos compiten por ocurrir primero (por ejemplo, un popup que se abre antes de que empieces a escucharlo) y el resultado depende de quién "gana".
Selector semántico
Un locator basado en el significado del elemento (su rol, su etiqueta, su texto) en vez de en detalles de implementación como clases CSS. Ver sección 05.
data-testid
Un atributo HTML que el equipo de desarrollo agrega solo para que los tests lo usen como selector — estable porque nadie más depende de él.
Page Object
Una clase que agrupa los locators y acciones de una página, en vez de repetirlos en cada test. Ver sección 25 (y aplicado a un proyecto completo en la sección 27).
CI (Integración Continua)
Un sistema automatizado (como GitHub Actions) que corre tus tests cada vez que se sube código nuevo, antes de fusionarlo.
Trace
Una grabación paso a paso de un test (screenshots, red, DOM) que puedes reproducir visualmente después de que falle. Ver sección 21.
Storage State
Una "foto" guardada de cookies + localStorage que te permite arrancar un test ya autenticado, sin repetir el login. Ver sección 14.
Snapshot / Visual regression
Comparar una captura de pantalla actual contra una guardada como referencia para detectar cambios visuales no intencionados. Ver sección 20.
Mock (peticiones de red)
Reemplazar la respuesta real de una petición HTTP por una inventada y controlada por ti, usando page.route(). Ver sección 17.
Polling
Revisar una condición repetidamente cada cierto tiempo hasta que se cumpla o se agote el timeout — así funciona waitForFunction por dentro.
01

Instalación

🟢 Principiante

Instala Playwright y los navegadores necesarios. El comando init lo configura todo automáticamente.

🎯¿Por qué importa? Antes de escribir un solo test necesitas el entorno listo. Este paso es la base de todo lo que sigue: sin los navegadores instalados, ningún test puede ejecutarse.
bash
# Inicializar proyecto (recomendado — genera config, carpetas y descarga browsers)
npm init playwright@latest

# Instalar solo el paquete en proyecto existente
npm install --save-dev @playwright/test

# Instalar navegadores
npx playwright install             # todos
npx playwright install chromium    # solo Chrome
npx playwright install firefox
npx playwright install webkit      # Safari

# Dependencias del sistema operativo
npx playwright install-deps
💡npm init playwright@latest es la forma más rápida: genera la carpeta tests/, el archivo playwright.config.ts y descarga los browsers en un solo paso.

🧠Autoevaluación — ¿Qué hace el comando npm init playwright@latest?

npm init playwright@latest es el scaffolding oficial: genera tests/, playwright.config.ts y descarga los navegadores automáticamente.

02

Estructura Básica de un Test

🟢 Principiante

Este es el esqueleto que vas a repetir en cada archivo de test: importar test y expect, describir el test con un nombre claro, y usar await en cada paso.

🎯¿Por qué importa? Todo test de Playwright sigue la misma forma: un nombre descriptivo, el fixture page, y await en cada paso porque el navegador es un proceso externo que tarda en responder. Con TypeScript, además, obtienes autocompletado de toda la API sin memorizar la documentación.
TypeScript
import { test, expect } from '@playwright/test';

test('flujo de login completo', async ({ page }) => {
  await page.goto('/login');                     // usa baseURL del config

  await page.getByLabel('Email').fill('user@test.com');
  await page.getByLabel('Contraseña').fill('secret123');
  await page.getByRole('button', { name: 'Entrar' }).click();

  // Verificar redirección al dashboard
  await expect(page).toHaveURL(/dashboard/);
  await expect(page.getByText('Bienvenido')).toBeVisible();
});

🧠Autoevaluación — En el ejemplo, page.goto('/login') navega a una URL relativa. ¿De dónde saca Playwright el dominio completo?

Cuando defines use: { baseURL: '...' } en la configuración, cualquier ruta relativa (/login, /dashboard) se completa automáticamente contra esa base.

03

Browser & Context

🟡 Intermedio

El Browser es la instancia del navegador. El BrowserContext es un perfil aislado (como una ventana privada). Ideal para simular múltiples usuarios simultáneos.

🎯¿Por qué importa? Entender la diferencia entre Browser y BrowserContext te permite simular varios usuarios (o sesiones) al mismo tiempo sin abrir varios navegadores.
TypeScript
import { chromium } from '@playwright/test';

const browser = await chromium.launch({
  headless: false,   // true = sin ventana visible
  slowMo: 50,         // ms de pausa entre acciones (útil para depurar)
});

const context = await browser.newContext({
  ignoreHTTPSErrors: true,
  viewport: { width: 1280, height: 720 },
  locale: 'es-MX',
  storageState: './auth.json',  // sesión guardada previamente
});

const page = await context.newPage();
await page.goto('https://mi-app.com');

await context.close();
await browser.close();
ℹ️En tests normales usas el page del fixture directamente. Crear browser/context manual es útil para tests con múltiples roles de usuario simultáneos.

🧠Autoevaluación — ¿Qué es un BrowserContext?

Un Browser puede tener muchos BrowserContexts, cada uno con sus propias cookies, storage y sesión — perfecto para tests que necesitan dos usuarios simultáneos (por ejemplo, probar un chat).

04

Navegación de Página

🟢 Principiante

Métodos para controlar la navegación: ir a URLs, recargar, usar historial y esperar estados de carga.

🎯¿Por qué importa? Saber esperar el momento correcto (URL, estado de carga) evita tests que fallan de forma aleatoria justo después de un login o un submit.
TypeScript
await page.goto('https://mi-app.com/productos');
await page.goto('/dashboard');                    // relativa a baseURL

await page.goBack();
await page.goForward();
await page.reload();

// Esperar a que la URL cambie (tras login, redirect…)
await page.waitForURL('**/dashboard');    // glob pattern
await page.waitForURL(/\/dashboard/);    // regex

// Esperar estados de carga
await page.waitForLoadState('load');
await page.waitForLoadState('domcontentloaded');
await page.waitForLoadState('networkidle');  // red inactiva ≥500ms

🧠Autoevaluación — ¿Qué diferencia hay entre waitForLoadState('load') y waitForLoadState('networkidle')?

"networkidle" es útil para apps que cargan datos por AJAX después del render inicial, pero Playwright recomienda preferir esperar un elemento visible en vez de depender de estados de red genéricos.

05

Locators

🟢 Principiante

Los locators seleccionan elementos. Playwright recomienda locators semánticos sobre CSS frágil porque son más resistentes a cambios de diseño.

🎯¿Por qué importa? Los locators son la base de cada interacción. Elegir uno frágil (como una clase CSS que cambia con cada rediseño) es la causa número uno de tests que se rompen sin que el bug sea real.
TypeScript — Todos los tipos
// ── CSS / XPath ──────────────────────────────────────
page.locator('button.submit')
page.locator('#form input[type="email"]')

// ── ✅ Semánticos (preferidos) ───────────────────────
page.getByRole('button', { name: 'Enviar' })
page.getByRole('textbox', { name: 'Email' })
page.getByRole('link', { name: 'Inicio' })
page.getByLabel('Contraseña')
page.getByPlaceholder('Escribe tu email')
page.getByText('Bienvenido')
page.getByText(/bienvenido/i)           // regex, sin distinción may/min
page.getByAltText('Logo empresa')
page.getByTestId('submit-btn')          // data-testid

// ── Filtrar y encadenar ──────────────────────────────
page.locator('.card').filter({ hasText: 'Disponible' })
page.locator('li').nth(2)               // tercer elemento
page.locator('li').first()
page.locator('li').last()

// ── Todos los elementos ──────────────────────────────
const items  = await page.locator('li').all();
const textos = await page.locator('li').allTextContents();
const total  = await page.locator('li').count();

// ── Estado ───────────────────────────────────────────
const visible = await page.locator('#modal').isVisible();
const enabled = await page.locator('button').isEnabled();
💡Orden de preferencia: getByRole › getByLabel › getByTestId › CSS. Los dos primeros reflejan cómo los usuarios reales interactúan con la interfaz.
Ejercicio — Encuentra los elementos correctos

Dado este HTML:

<form>
  <label for="u">Usuario</label>
  <input id="u" placeholder="Tu nombre de usuario">
  <button type="submit">Crear cuenta</button>
</form>

Escribe tres locators diferentes para seleccionar el campo de texto, y uno para el botón de submit. Usa la forma más semántica posible.

Ver solución
Solución
// Campo de texto — 3 formas
page.getByLabel('Usuario')                          // ✅ mejor
page.getByPlaceholder('Tu nombre de usuario')         // ✅ también válido
page.getByRole('textbox', { name: 'Usuario' })       // ✅ semántico

// Botón
page.getByRole('button', { name: 'Crear cuenta' })   // ✅ lo mejor
page.getByText('Crear cuenta')                       // funciona pero menos preciso

🧠Autoevaluación — Según el orden de preferencia recomendado, ¿cuál locator deberías usar primero?

El orden recomendado es getByRole › getByLabel › getByTestId › CSS. Los dos primeros son "semánticos": dependen del significado del elemento (su rol, su etiqueta), no de detalles de implementación que cambian con el diseño.

06

Acciones

🟢 Principiante

Playwright espera automáticamente a que el elemento sea visible, habilitado y estable antes de ejecutar cada acción.

🎯¿Por qué importa? Playwright ya espera automáticamente a que un elemento sea visible y esté habilitado antes de actuar. No necesitas escribir ese código tú mismo, pero sí necesitas saber qué acción usar en cada caso.
TypeScript
const btn   = page.getByRole('button', { name: 'Enviar' });
const email = page.getByLabel('Email');

// Clics
await btn.click();
await btn.dblclick();
await btn.click({ button: 'right' });
await btn.click({ modifiers: ['Control'] });

// Formularios
await email.fill('user@correo.com');   // limpia y escribe
await email.clear();
await email.type('lento', { delay: 80 }); // simula tecleo real
await email.press('Tab');
await page.keyboard.press('Control+A');

// Checkbox / Radio
await page.getByLabel('Recordarme').check();
await page.getByLabel('Recordarme').uncheck();

// Select
await page.getByLabel('País').selectOption('México');
await page.getByLabel('Idiomas').selectOption(['es', 'en']);

// Hover, foco, drag
await btn.hover();
await page.locator('#card').dragTo(page.locator('#done'));
Ejercicio — Completa un formulario de registro

Escribe un test que:
1. Navegue a https://practice.expandtesting.com/register
2. Rellene el campo Username con miusuario
3. Rellene Password y Confirm Password con MiClave123!
4. Marque el checkbox de términos y condiciones
5. Haga clic en el botón Register

Ver solución
Solución
test('registro de nuevo usuario', async ({ page }) => {
  await page.goto('https://practice.expandtesting.com/register');

  await page.getByLabel('Username').fill('miusuario');
  await page.getByLabel('Password', { exact: true }).fill('MiClave123!');
  await page.getByLabel('Confirm Password').fill('MiClave123!');
  await page.getByLabel(/terms/i).check();
  await page.getByRole('button', { name: 'Register' }).click();

  await expect(page.getByText(/successfully/i)).toBeVisible();
});

🧠Autoevaluación — ¿Qué hace fill() que type() no hace?

fill() es rápido y directo (limpia y escribe de golpe) — úsalo casi siempre. type() simula pulsaciones reales con delay, útil solo cuando pruebas comportamiento que depende de eventos de teclado (como un autocompletado).

07

Assertions (Expect)

🟢 Principiante

Playwright reintenta las assertions automáticamente durante el timeout (5 s por defecto). No necesitas esperas manuales antes de verificar.

🎯¿Por qué importa? Las assertions de Playwright reintentan solas durante varios segundos. Si entiendes esto, dejas de escribir esperas manuales antes de cada verificación.
TypeScript — Assertions más usadas
// Visibilidad y estado
await expect(locator).toBeVisible();
await expect(locator).toBeHidden();
await expect(locator).toBeEnabled();
await expect(locator).toBeDisabled();
await expect(locator).toBeChecked();

// Contenido
await expect(locator).toHaveText('Bienvenido, Carlos');  // exacto
await expect(locator).toHaveText(/bienvenido/i);
await expect(locator).toContainText('Carlos');
await expect(locator).toHaveValue('carlos@email.com');
await expect(locator).toHaveCount(5);

// Atributos y estilos
await expect(locator).toHaveAttribute('href', '/perfil');
await expect(locator).toHaveClass('btn-active');
await expect(locator).toHaveCSS('color', 'rgb(255, 0, 0)');

// Página
await expect(page).toHaveTitle(/Dashboard/);
await expect(page).toHaveURL(/\/home/);

// Negación
await expect(locator).not.toBeVisible();
await expect(page).not.toHaveURL(/error/);
Ejercicio — Verifica el estado de una página

Después de hacer login en una app, escribe assertions para verificar:
1. La URL contiene /dashboard
2. Hay un <h1> que dice "Panel de control"
3. El botón "Cerrar sesión" es visible
4. El botón "Login" ya no está visible

Ver solución
Solución
await expect(page).toHaveURL(/\/dashboard/);
await expect(page.getByRole('heading', { name: 'Panel de control' })).toBeVisible();
await expect(page.getByRole('button', { name: 'Cerrar sesión' })).toBeVisible();
await expect(page.getByRole('button', { name: 'Login' })).not.toBeVisible();

🧠Autoevaluación — Haces clic en un botón que abre un modal con animación y luego escribes await expect(locator).toBeVisible(). ¿Necesitas un waitForTimeout antes?

Esta es una de las características más poderosas de Playwright: las assertions con expect no fallan al primer intento, sino que reintentan hasta cumplirse o agotar el timeout — por eso casi nunca necesitas waitForTimeout.

08

Waits (Esperas Explícitas)

🟡 Intermedio

Playwright tiene auto-waiting en casi todas las acciones. Estas funciones son para condiciones avanzadas que el auto-wait no cubre.

🎯¿Por qué importa? El auto-wait cubre la mayoría de los casos, pero cuando necesitas esperar una condición muy específica (una petición de red, un contador en el DOM) hacen falta estas herramientas.
TypeScript
// Esperar a que desaparezca un spinner y aparezca el resultado
await page.locator('.spinner').waitFor({ state: 'hidden' });
await page.locator('.resultado').waitFor({ state: 'visible' });
// Estados: 'visible' | 'hidden' | 'attached' | 'detached'

// Esperar cambio de URL (tras submit de formulario)
await page.waitForURL('**/confirmacion', { timeout: 15000 });

// Esperar condición personalizada (polling)
await page.waitForFunction(() =>
  document.querySelectorAll('.producto').length >= 10
);

// Esperar respuesta de red + acción en simultáneo
const [response] = await Promise.all([
  page.waitForResponse('**/api/productos'),
  page.getByRole('button', { name: 'Cargar más' }).click(),
]);
const data = await response.json();
⚠️Evita waitForTimeout(5000). Los timeouts fijos hacen tests lentos e inestables en CI. Siempre espera una condición, no un tiempo arbitrario.

🧠Autoevaluación — ¿Cuál es el problema principal de usar waitForTimeout(5000) en vez de esperar una condición?

Un tiempo fijo nunca es exacto: si sobra, desperdicias segundos en cada ejecución; si falta (por ejemplo en un runner de CI más lento), el test falla aunque la app funcione bien. Esperar una condición real resuelve ambos problemas.

09

Frames (iFrames)

🟡 Intermedio

Para interactuar con un <iframe> primero obtén el frame. Luego lo usas exactamente igual que page.

🎯¿Por qué importa? Un iframe es literalmente un documento HTML distinto embebido en la página. Playwright necesita saber explícitamente que quieres ‘entrar’ a ese documento antes de buscar elementos dentro.
TypeScript
// frameLocator — método recomendado
const frame = page.frameLocator('iframe[name="pago"]');

await frame.getByLabel('Número de tarjeta').fill('4111 1111 1111 1111');
await frame.getByLabel('CVV').fill('123');
await frame.getByRole('button', { name: 'Pagar' }).click();

// Objeto Frame (alternativa)
const f = page.frame({ name: 'mi-iframe' });
await f.locator('input.nombre').fill('Juan');

🧠Autoevaluación — ¿Qué método se recomienda para trabajar con un iframe?

frameLocator() es la forma moderna y recomendada: devuelve un objeto con la misma API que page, así que puedes encadenar .getByLabel(), .click(), etc. sin cambiar tu forma de pensar.

10

Dialogs (alert, confirm, prompt)

🟡 Intermedio

Los diálogos nativos del navegador se capturan con el evento dialog. Registra el handler ANTES de la acción que lo dispara.

🎯¿Por qué importa? Los diálogos nativos (alert, confirm, prompt) bloquean el navegador. Si no registras el handler a tiempo, tu test se queda colgado esperando algo que nunca vas a poder pulsar.
TypeScript
// Aceptar cualquier diálogo
page.on('dialog', dialog => dialog.accept());

// Manejar según tipo
page.on('dialog', async dialog => {
  console.log(dialog.type);        // 'alert' | 'confirm' | 'prompt'
  console.log(dialog.message());
  if (dialog.type === 'prompt') {
    await dialog.accept('Mi respuesta');
  } else {
    await dialog.accept();
  }
});

// Solo el PRÓXIMO diálogo (no todos los futuros)
page.once('dialog', d => d.accept());
await page.getByRole('button', { name: 'Eliminar cuenta' }).click();

🧠Autoevaluación — ¿Por qué hay que registrar page.on('dialog', ...) ANTES del clic que dispara el diálogo?

Los diálogos nativos son bloqueantes por diseño del navegador. El patrón correcto siempre es: primero page.on('dialog', ...), después la acción que lo abre — nunca al revés.

11

Popups (ventanas nuevas)

🟡 Intermedio

Ventanas abiertas con target="_blank". Escucha el evento antes del clic que las abre.

🎯¿Por qué importa? Un enlace con target="_blank" abre una pestaña nueva casi instantáneamente. Si escuchas el evento después del clic, puedes perderlo.
TypeScript
const [popup] = await Promise.all([
  page.waitForEvent('popup'),
  page.getByRole('link', { name: 'Abrir en nueva pestaña' }).click(),
]);
await popup.waitForLoadState();
await expect(popup).toHaveURL(/terminos/);
await popup.close();

🧠Autoevaluación — ¿Por qué se usa Promise.all([page.waitForEvent('popup'), link.click()]) en vez de hacer el clic y luego esperar?

Es el mismo patrón que evita perder el evento "dialog": registrar la escucha y disparar la acción en el mismo instante, no en secuencia.

12

File Upload

🟡 Intermedio

Simula la selección de archivos sin abrir el diálogo del sistema operativo.

🎯¿Por qué importa? Los selectores de archivo del sistema operativo no se pueden automatizar directamente. Playwright los evita por completo inyectando el archivo en el input.
TypeScript
await page.setInputFiles('input[type="file"]', './foto.png');
await page.setInputFiles('input[type="file"]', ['./a.png', './b.pdf']);
await page.setInputFiles('input[type="file"]', []);  // limpiar

// Con locator
await page.getByLabel('Sube tu CV').setInputFiles('./mi-cv.pdf');

🧠Autoevaluación — ¿Qué hace setInputFiles('input[type="file"]', []) con un array vacío?

Pasar un array vacío es la forma de simular que el usuario canceló o borró su selección, sin tener que interactuar con ningún diálogo del sistema.

13

Descargas

🟡 Intermedio

Captura archivos descargados. El patrón es el mismo que con popups: escucha antes de la acción.

🎯¿Por qué importa? Igual que con popups y dialogs, una descarga es un evento que puede dispararse muy rápido. El patrón de ‘escuchar antes de actuar’ se repite en Playwright por la misma razón.
TypeScript
const [download] = await Promise.all([
  page.waitForEvent('download'),
  page.getByRole('button', { name: 'Descargar Reporte' }).click(),
]);
console.log(download.suggestedFilename());         // "reporte.pdf"
await download.saveAs('./reportes/reporte.pdf');
await download.delete();                            // limpia el temporal

🧠Autoevaluación — Después de capturar el evento 'download', ¿qué hace download.saveAs(ruta)?

Playwright guarda cada descarga en un archivo temporal automáticamente; saveAs() es lo que mueve ese archivo a donde tú decidas para inspeccionarlo o guardarlo.

API Testing (Request)

🟠 Avanzado

Playwright puede hacer peticiones HTTP directamente sin abrir un navegador. Ideal para preparar datos de test o verificar endpoints REST.

🎯¿Por qué importa? No todo test necesita un navegador. Crear datos de prueba (o verificar un backend) por API directa es mucho más rápido que hacerlo clic por clic en la UI.
TypeScript
test('API — CRUD usuario', async ({ request }) => {
  // GET
  const res = await request.get('https://api.app.com/usuarios');
  await expect(res).toBeOK();
  const lista = await res.json();

  // POST — crear
  const post = await request.post('https://api.app.com/usuarios', {
    data: { nombre: 'Ana García', email: 'ana@test.com' },
    headers: { Authorization: 'Bearer mi-token' },
  });
  await expect(post).toHaveStatus(201);

  // PUT / DELETE
  const { id } = await post.json();
  await request.put(`/usuarios/${id}`, { data: { nombre: 'Ana López' } });
  await request.delete(`/usuarios/${id}`);
  await request.dispose();
});

🧠Autoevaluación — ¿Cuál es la ventaja clave de usar el fixture request en vez de simular la UI para preparar datos de test?

Usar request para crear o borrar datos de setup (en vez de rellenar formularios) hace que tus tests de UI se enfoquen solo en lo que realmente quieres probar, y corran mucho más rápido.

Interceptar y Mockear Peticiones de Red Nuevo

🟠 Avanzado

Con page.route() interceptas cualquier petición que haga la página antes de que llegue al servidor, y decides qué responder. Sirve para simular errores del backend, acelerar tests bloqueando recursos innecesarios, o probar la UI sin depender de un servidor real.

🎯¿Por qué importa? Depender de un backend real hace los tests lentos, inestables y a veces imposibles de escribir (¿cómo provocas un error 500 a propósito?). Interceptar la red te da control total sobre lo que la página recibe.
TypeScript — Mockear una respuesta completa
await page.route('**/api/usuarios', async route => {
  await route.fulfill({
    status: 200,
    contentType: 'application/json',
    body: JSON.stringify([{ id: 1, nombre: 'Usuario de prueba' }]),
  });
});
await page.goto('/usuarios');
// La página nunca llega a tocar el backend real
TypeScript — Modificar una respuesta real, y bloquear recursos
await page.route('**/api/usuarios', async route => {
  const response = await route.fetch();            // deja pasar la petición real
  const body = await response.json();
  body.push({ id: 999, nombre: 'Usuario inyectado' }); // modificas el resultado
  await route.fulfill({ response, body: JSON.stringify(body) });
});

// Bloquear peticiones que no necesitas — tests más rápidos y estables
await page.route('**/*.{png,jpg,jpeg}', route => route.abort());
await page.route('**/analytics/**', route => route.abort());
💡Para simular un error del servidor solo necesitas cambiar el status: route.fulfill({'{'} status: 500, body: 'Error interno' {'}'}) — así pruebas cómo reacciona tu UI sin tener que romper el backend real.
❌ Sin mock — depende de datos reales
// El test falla si el backend está caído,
// si otro test ya borró ese usuario, etc.
await page.goto('/usuarios');
await expect(page.getByText('Ana García')).toBeVisible();
✅ Con mock — determinístico
// El resultado es siempre el mismo,
// sin importar el estado del backend
await page.route('**/api/usuarios', route => route.fulfill({ body: '[...]' }));
await page.goto('/usuarios');
Ejercicio — Simula un error del servidor

Usa page.route() para interceptar **/api/pedido y responder con status 500. Luego navega a /pedido y verifica que la página muestra el texto "Ocurrió un error".

Ver solución
Solución

  status: 500,
  body: 'Error interno',
}));

await expect(page.getByText('Ocurrió un error')).toBeVisible();

🧠Autoevaluación — ¿Qué hace route.fetch() seguido de route.fulfill({ response, body: ... }) en un handler de page.route()?

route.fetch() ejecuta la petición original y te da la respuesta real; a partir de ahí puedes leerla, modificarla (por ejemplo agregar un elemento a la lista) y entregársela a la página con fulfill() — a diferencia de route.fulfill() directo, que nunca toca el servidor.

Anotaciones de Tests

🟡 Intermedio

TypeScript
test.describe('Autenticación', () => {
  test.beforeAll(async () => { /* una vez antes del grupo */ });
  test.afterAll(async  () => { /* una vez después del grupo */ });
  test.beforeEach(async ({ page }) => { await page.goto('/login'); });
  test.afterEach(async  ({ page }) => { /* limpieza */ });

  test('login exitoso', async ({ page }) => { ... });
  test.skip('SSO — no implementado', async () => {});
  test.fixme('reset contraseña — flaky', async () => {});
});

test.only('depurar este test', async ({ page }) => { ... });  // solo este
test.slow('test pesado', async ({ page }) => { ... });       // triple timeout

🧠Autoevaluación — ¿Cuál es el riesgo real de dejar test.only() en un commit?

test.only es útil mientras depuras un test localmente, pero si llega a main, el CI deja de verificar todo lo demás sin ningún error visible — por eso conviene un linter que lo detecte antes del commit.

Page Object Model (POM) Nuevo

🟠 Avanzado

Un Page Object es una clase que agrupa los locators y las acciones de una página (o componente) en un solo lugar. En vez de escribir page.getByLabel('Email').fill(...) en cada test, el test llama a un método con nombre de negocio como loginPage.login(usuario, clave).

🎯¿Por qué importa? Repetir los mismos locators en cada test es la razón más común por la que una suite se vuelve imposible de mantener. El patrón Page Object soluciona esto agrupando cada página en una clase reutilizable.
pages/LoginPage.ts
import { type Page, type Locator } from '@playwright/test';

export class LoginPage {
  readonly page: Page;
  readonly email: Locator;
  readonly password: Locator;
  readonly submitBtn: Locator;

  constructor(page: Page) {
    this.page = page;
    // Los locators se definen una sola vez, aquí
    this.email = page.getByLabel('Email');
    this.password = page.getByLabel('Contraseña');
    this.submitBtn = page.getByRole('button', { name: 'Entrar' });
  }

  async goto() {
    await this.page.goto('/login');
  }

  // El método expresa INTENCIÓN, no pasos técnicos
  async login(usuario: string, clave: string) {
    await this.email.fill(usuario);
    await this.password.fill(clave);
    await this.submitBtn.click();
  }
}
tests/login.spec.ts — el test ya no conoce ningún locator
import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test('login exitoso', async ({ page }) => {
  const loginPage = new LoginPage(page);

  await loginPage.goto();
  await loginPage.login('user@test.com', 'secret123');

  await expect(page).toHaveURL(/dashboard/);
});
💡Si el diseño cambia y el campo "Contraseña" pasa a llamarse "Clave de acceso", corriges un solo locator en LoginPage.ts — ningún test necesita tocarse.
❌ Sin POM — locators repetidos en cada test
test('test 1', async ({ page }) => {
  await page.getByLabel('Email').fill('a@test.com');
  await page.getByLabel('Contraseña').fill('123');
  await page.getByRole('button', { name: 'Entrar' }).click();
});
test('test 2', async ({ page }) => {
  await page.getByLabel('Email').fill('b@test.com');
  // ...mismos locators, otra vez
});
✅ Con POM — un solo lugar para mantener
test('test 1', async ({ page }) => {
  await new LoginPage(page).login('a@test.com', '123');
});
test('test 2', async ({ page }) => {
  await new LoginPage(page).login('b@test.com', '456');
});
Ejercicio — Crea tu propio Page Object

Convierte esta lógica repetida en un Page Object llamado SearchPage con un método search(termino: string):

Fixtures Personalizados Nuevo

🟠 Avanzado

Un fixture personalizado te deja inyectar algo directamente en la firma del test — como un Page Object ya instanciado y con login hecho — sin repetir new LoginPage(page) ni beforeEach en cada archivo. Es la forma en que se organizan los frameworks de Playwright en proyectos reales.

🎯¿Por qué importa? Repetir 'new LoginPage(page)' y la navegación inicial en el beforeEach de cada archivo es exactamente el tipo de duplicación que un fixture personalizado elimina — lo defines una vez y cualquier test lo pide por nombre.
fixtures/pages.fixture.ts
import { test as base } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

type MisFixtures = { loginPage: LoginPage };

export const test = base.extend<MisFixtures>({
  loginPage: async ({ page }, use) => {
    const loginPage = new LoginPage(page);
    await loginPage.goto();               // setup — corre ANTES del test

    await use(loginPage);                 // aquí el test recibe el fixture y corre

    // código después de use() = teardown, corre DESPUÉS del test
  },
});

export { expect } from '@playwright/test';
tests/login.spec.ts — el test pide el fixture por nombre
import { test, expect } from '../fixtures/pages.fixture';

test('login exitoso', async ({ loginPage, page }) => {
  // loginPage ya existe y ya navegó — el setup ya pasó

});
💡use(valor) es el punto donde el fixture entrega el valor al test. Todo lo que escribas después de ese await use(...) corre como teardown automático al terminar el test — incluso si el test falló.
❌ Sin fixture — repetido en cada archivo
test.beforeEach(async ({ page }) => {
  const loginPage = new LoginPage(page);
  await loginPage.goto();
});
// ...y otra vez en el siguiente archivo de test
✅ Con fixture — una sola definición
test('...', async ({ loginPage }) => {
  // listo para usar, en cualquier archivo
});

pages/TodoPage.ts — el Page Object del proyecto
import { type Page, type Locator, expect } from '@playwright/test';

export class TodoPage {
  readonly page: Page;
  readonly newTodoInput: Locator;
  readonly todoItems: Locator;
  readonly clearCompletedBtn: Locator;
  readonly toggleAllCheckbox: Locator;

  constructor(page: Page) {
    this.page = page;
    this.newTodoInput = page.getByPlaceholder('What needs to be done?');
    this.todoItems = page.locator('.todo-list li');
    this.clearCompletedBtn = page.getByRole('button', { name: 'Clear completed' });
    this.toggleAllCheckbox = page.locator('label[for="toggle-all"]');
  }

  async goto() {
    await this.page.goto('/');
    await expect(this.page).toHaveTitle(/TodoMVC/);
  }

  async addTodo(titulo: string) {
    await this.newTodoInput.fill(titulo);
    await this.newTodoInput.press('Enter');
  }

  async toggleFirst() {
    await this.todoItems.first().locator('.toggle').click();
  }

  async editFirst(nuevoTexto: string) {
    await this.todoItems.first().dblclick();
    const edit = this.page.locator('.todo-list li.editing input.edit');
    await edit.fill(nuevoTexto);
    await edit.press('Enter');
  }

  async filterBy(nombre: 'All' | 'Active' | 'Completed') {
    await this.page.getByRole('link', { name: nombre }).click();
  }
}

Errores Frecuentes y Cómo Solucionarlos Nuevo

🟡 Intermedio

Los errores más comunes al aprender Playwright, con el código problemático y la corrección explicada.

🎯¿Por qué importa? Estos seis errores explican la mayoría de los tests ‘flaky’ o silenciosamente rotos que vas a encontrar en cualquier proyecto real. Reconocerlos te ahorra horas de depuración.

❶ Usar selector CSS cuando el elemento cambia clase con el diseño

❌ Frágil
// Si renombran la clase CSS, el test rompe
await page.locator('.btn-primary-v2').click();
await page.locator('div > form > button:nth-child(3)').click();
✅ Robusto
// El texto y rol del botón raramente cambian
await page.getByRole('button', { name: 'Guardar cambios' }).click();

❷ Race condition: actuar antes de que el popup esté listo

❌ Race condition
// El popup puede abrir ANTES de que
// ejecutes waitForEvent — lo pierdes
await page.click('a[target="_blank"]');
const popup = await page.waitForEvent('popup'); // tarde
✅ Correcto
// Promise.all inicia AMBOS antes de await
const [popup] = await Promise.all([
  page.waitForEvent('popup'),   // escucha primero
  page.click('a[target="_blank"]'),
]);

❸ Usar timeouts fijos para esperar carga

❌ Frágil y lento
await page.click('#cargar');
// 3 s en máquina rápida = desperdicio
// 3 s en CI lento = fallo esporádico
await page.waitForTimeout(3000);
await expect(page.locator('.lista')).toBeVisible();
✅ Basado en condición
await page.click('#cargar');
// Espera exactamente lo necesario
await expect(page.locator('.lista')).toBeVisible();
// El expect reintenta por ti

❹ No usar await en una assertion

❌ Test pasa siempre (bug silencioso)
// Sin await, la assertion NO se ejecuta
// El test pasa aunque falle la condición
expect(page.locator('h1')).toHaveText('Hola');
// ⬆️ Esto devuelve una Promise sin resolver
✅ Con await
// Siempre await en assertions de Playwright
await expect(page.locator('h1')).toHaveText('Hola');
// ⬆️ Espera y verifica correctamente

❺ Registrar el handler de dialog después del clic que lo dispara

❌ El diálogo se cierra solo
await page.click('#eliminar'); // dialog aparece
// Registrar aquí es demasiado tarde
page.on('dialog', d => d.accept());
✅ Handler antes del clic
// Registrar ANTES de la acción
page.once('dialog', d => d.accept());
await page.click('#eliminar');

❻ Usar test.only y olvidarlo en el código

🚨Peligro silencioso: Si haces commit con test.only() en el código, solo ese test correrá en el CI y todos los demás quedarán sin ejecutarse. Usa --grep en la línea de comandos en su lugar, o instala el plugin ESLint de Playwright que detecta test.only.
❌ No hagas commit con esto
test.only('mi test', async ({ page }) => {
  // Si haces commit, el CI solo ejecuta este test
});
✅ Filtra desde CLI
# Correr solo un test por nombre
npx playwright test -g "mi test"

# O usar --debug para ese test
npx playwright test -g "mi test" --debug
💡Instala eslint-plugin-playwright para detectar automáticamente test.only, waitForTimeout hardcodeados y otros anti-patrones en tu código.

🧠Autoevaluación — De los seis errores de esta sección, ¿cuál puede hacer que un test "pase" aunque el comportamiento real esté roto?

Sin await, expect(locator).toHaveText(...) devuelve una Promise que nadie espera — el test termina antes de que la verificación real ocurra, y Playwright lo reporta como exitoso. Es el error más peligroso porque no lanza ningún error visible.

// 1. ¿Por qué Playwright y no Selenium?
//    Auto-waiting integrado (menos tests "flaky"), una sola API
//    para UI + peticiones de red, y mejor tooling: Trace Viewer,
//    UI Mode, codegen. Selenium requiere waits manuales y más
//    configuración para llegar al mismo punto.

// 2. ¿Qué es un BrowserContext?
//    Un perfil de navegador aislado — como una ventana privada.
//    Permite simular varios usuarios en paralelo. Ver sección 03.

// 3. ¿Cómo funciona el auto-waiting?
//    Antes de cada acción, Playwright espera a que el elemento
//    exista, sea visible, esté habilitado y deje de moverse —
//    sin que el test tenga que pedirlo explícitamente.

// 4. ¿Cuál es el orden de prioridad de locators?
//    getByRole > getByLabel / getByPlaceholder > getByTestId > CSS > XPath.
//    Los semánticos primero porque reflejan cómo interactúa un usuario real.

// 5. ¿Qué es un fixture?
//    Una forma de inyectar dependencias (como un Page Object ya
//    listo) directamente en la firma del test. Ver sección 26.

// 6. ¿Cómo corre Playwright los tests en paralelo?
//    Reparte los archivos de test entre varios "workers"
//    (procesos), configurables con `workers` en playwright.config.ts.

// 7. ¿Qué es un Page Object y por qué se usa?
//    Una clase que agrupa los locators y acciones de una página.
//    El test expresa intención de negocio, no pasos técnicos. Ver sección 25.

// 8. ¿Cómo evitas depender de un backend real en tus tests?
//    Con page.route() interceptas la petición y respondes con
//    datos mockeados — la UI se prueba igual, sin backend. Ver sección 17.
📌Estructura de carpetas típica en un proyecto de Playwright: tests/ (specs), pages/ (Page Objects), fixtures/ (fixtures personalizados) y playwright.config.ts en la raíz. Ver sección 22.

🧠Autoevaluación — Un entrevistador te pregunta por qué preferirías Playwright sobre Selenium en un proyecto nuevo. ¿Cuál es la mejor respuesta corta?

Selenium sí soporta TypeScript y sí puede paralelizar con configuración extra, y sigue activamente mantenido — la ventaja real de Playwright es el auto-waiting nativo, la API unificada (UI + request) y herramientas como el Trace Viewer que reducen mucho el tiempo de depuración.

📊0 / 8 respondidas

🧠Pregunta 1 — ¿Cuál es la diferencia real entre locator.click() y locator.dispatchEvent('click')?

click() pasa por todo el auto-waiting de Playwright antes de actuar. dispatchEvent() es una puerta trasera de bajo nivel, útil solo cuando un elemento no responde a eventos reales de usuario (poco común).

🧠Pregunta 2 — ¿Qué hace expect.soft() a diferencia de un expect() normal?

Con assertions "soft", el test sigue corriendo aunque una falle — útil cuando quieres ver TODOS los problemas de una página en un solo reporte, en vez de detenerte en el primero.

🧠Pregunta 3 — ¿Para qué sirve test.step()?

test.step('nombre', async () => {'{'} ... {'}'}) no cambia el comportamiento del test, pero hace el reporte y el trace mucho más legibles al dividir un test largo en fases con nombre.

🧠Pregunta 4 — ¿Qué problema resuelve globalSetup en playwright.config.ts?

globalSetup es el lugar recomendado para preparar cosas costosas (como autenticarse) una única vez, y que cada test arranque ya con ese estado guardado.

🧠Pregunta 5 — ¿Qué es el "strict mode" de los locators en Playwright?

El "strict mode" es una protección: si tu locator es ambiguo (matchea 2+ elementos), Playwright prefiere fallar ruidosamente antes que adivinar cuál querías — evita bugs silenciosos.

🧠Pregunta 6 — ¿Qué diferencia hay entre locator.waitFor({'{'} state: 'visible' {'}'}) y await expect(locator).toBeVisible()?

Ambos esperan la misma condición por dentro, pero toBeVisible() es una assertion pensada para ser el punto de verificación del test — se reporta como tal cuando falla.

🧠Pregunta 7 — ¿Qué hace expect(async () => {'{'} ... {'}'}).toPass()?

toPass() extiende el reintento automático de Playwright a CUALQUIER lógica, no solo a una assertion — útil cuando necesitas varios pasos dentro del mismo reintento.

🧠Pregunta 8 — ¿Qué es el "sharding" (--shard=1/3) en Playwright?

Sharding es distinto de workers (paralelismo dentro de UNA máquina): reparte los archivos de test entre MÁQUINAS distintas, cada una corriendo su propio conjunto de workers.
